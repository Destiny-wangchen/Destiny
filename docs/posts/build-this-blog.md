## 先打个比方，弄懂三样东西

想象你想在城里开一家自己的小书店，需要什么？

**1. 书稿 —— Markdown 文件**

你写的文章就是书稿。Markdown 是一种「打字时顺手加几个小符号」的写作方式，比如在字两边打两个星号，发布后那段字就自动加粗。写文章和写 Word 没区别，只是多了几个小符号。

**2. 一块免费的地皮 —— GitHub**

GitHub 是一个全球程序员都在用的「网盘 + 仓库」，免费。你可以把自己的所有文件存上去，它还会帮你记录每一次修改（改错了随时能退回上一步）。

**3. 免费装修并开放参观 —— GitHub Pages**

光有仓库还不够，得让别人能打开你的网站。GitHub 自带一项叫 Pages 的免费服务：你说一声「把我仓库里的博客开放出去」，它就自动帮你生成一个网址，全世界都能访问。

所以整个流程就是：**写书稿 → 存进仓库 → 一键开放**。没有租金，没有服务器，不用求人。

## 动手前的准备（只需要做一次）

1. **注册一个 GitHub 账号**：打开 github.com，点 Sign up，填邮箱密码，跟注册任何网站一样
2. **在你的电脑上装 Node.js**：它是「印刷机」，负责把你的书稿变成能打开的网页。去 nodejs.org 下载安装包，一路点「下一步」装完就行
3. **认识一下「命令行」**：Windows 上按 Win 键输入 powershell 回车，会弹出一个黑底（或白底）的窗口。别怕，它就是「用打字跟电脑对话」的窗口，下面让你输入什么就复制粘贴什么

## 五步搭好博客

### 第 1 步：从模板开始

从零造房子太累，先用现成的毛坯房。把这个仓库（github.com/Destiny-wangchen/Destiny）下载到你电脑上，或者按它的结构新建文件夹。目录大概长这样：

```text
我的博客/
├── docs/
│   ├── index.md        ← 首页内容
│   ├── posts/          ← 你的所有文章，一篇一个文件
│   └── .vitepress/     ← 网站的「设置」，一般不用动
└── package.json        ← 项目说明书
```

### 第 2 步：把它跑起来看看

在博客文件夹里打开命令行，输入两行字：

```bash
npm install    ← 第一次要等几分钟，下载各种零件
npm run dev    ← 启动！
```

然后浏览器打开它提示的网址（一般是 localhost:5173），就能看到你的博客了。**改文件保存，网页自动刷新**，跟编辑实时预览一样。

### 第 3 步：写你的第一篇文章

打开 `docs/posts` 文件夹，新建一个文本文件改名为 `my-first-post.md`（注意后缀是 .md 不是 .txt），用任何文本编辑器打开，开头写上这几行：

```text
---
title: 我的第一篇文章
date: 2026-09-12
tags:
  - 生活
---

从这里开始写正文……
```

上面三横线之间的部分是「文章的档案卡」：标题、日期、标签。保存后刷新网页，首页自动就会出现这篇文章——**不用改任何代码**。

### 第 4 步：上传到 GitHub

在 GitHub 网页上点 New repository（新建仓库），起个名字。然后在博客文件夹的命令行里：

```bash
git add -A                    ← 把所有文件打包装车
git commit -m "第一次上架"     ← 贴个标签说明这次改了什么
git push                      ← 发车，推到 GitHub
```

第一次推会要求登录，跟着提示操作就行。

### 第 5 步：打开「开放参观」的开关

回到 GitHub 网页，进入你的仓库：

**Settings → Pages → Source 选 GitHub Actions**，保存。

再去仓库里加一个「自动部署」的配置文件（告诉 GitHub：每次我上传，你就自动重新生成网站）。这个博客仓库里的 `.github/workflows/deploy.yml` 就是现成的，抄过去能用。

以后每次 `git push`，一分钟左右网站自动更新。完事。

## 常见问题

**要花钱吗？** 不用。GitHub 账号、Pages 托管、Node.js 全部免费。

**要学编程吗？** 日常写文章完全不用。上面出现的命令复制粘贴就行，理解成「咒语」也无妨——念了就生效。

**能换成自己的网址吗？** 能。GitHub Pages 支持绑定自定义域名，设置里加一下就行，域名一年几十块（不买也完全能用免费网址）。

**文章写错了/误删了怎么办？** 这就是用 GitHub 的好处——它记得每一次修改，随时能找回任何一版。

## 给博客加评论

> 第一讲解决「读者说话」的问题。

### 为什么评论这件事不简单

你的博客是一台「印刷机」提前印好的：文章在发布的那一刻就变成了固定的网页，寄存在 GitHub 那块免费地皮上。这样做的好处是加载飞快、不花钱，但有一个天然的缺陷——

**印出来的书，读者没法在上面写字。**

想让读者留言，只有两条路：

1. **自己租一间机房**，专门负责收留言、存留言。这要花钱、要维护，书还没卖出几本，先雇了个保安。
2. **借别人的客厅**。反正大家都有 GitHub 账号，那就让留言写到 GitHub 的「讨论区」里去，你的网页只负责摆一块留言板，把留言展示出来。

第二条路就是这一讲要讲的方案，它的名字叫 **Giscus**。整个体系完全免费，因为你借的客厅本来就是免费的。

### 它是怎么运作的

打个比方：你在自家书店后墙挂了一块留言板，但这块板子是魔法玻璃——

- 读者在你店里写下留言
- 留言实际存进了 GitHub 上你仓库的「讨论区」（Discussions，可以理解成仓库自带的公开留言室）
- 其他读者打开你的文章，魔法玻璃自动把 GitHub 上的留言照出来

所以：**留言不会丢（GitHub 帮你存着）、不要钱、你随时能去 GitHub 上管理甚至删掉它们**。唯一的门槛是：想留言的读者也得有 GitHub 账号。对技术博客来说这几乎不是门槛；对纯生活博客来说，你要考虑一下读者群里有多少人愿意为留言注册一个账号。

### 动手前的准备（只需要做一次）

1. **打开仓库的讨论区**：去你的 GitHub 仓库页面，点 Settings → General，往下翻到 Features，把 **Discussions** 勾上
2. **给留言板发一块通行证**：打开 github.com/apps/giscus，点 Install，选择你的博客仓库。这一步是授权 Giscus 这个「中间人」替你的网页去读写讨论区

### 把留言板挂到墙上

在你的博客项目里新建一个文件，比如 `docs/.vitepress/theme/components/Giscus.vue`，内容如下（可以直接抄，把几个 ID 换成你自己的）：

```vue
<template>
  <div ref="box"></div>
</template>

<script setup>
import { onMounted, ref } from 'vue'

const box = ref(null)

function create() {
  const s = document.createElement('script')
  s.src = 'https://giscus.app/client.js'
  s.async = true
  s.crossOrigin = 'anonymous'
  s.setAttribute('data-repo', '你的用户名/你的仓库名')   // ← 换成你的
  s.setAttribute('data-repo-id', '从 giscus.app 拿')      // ← 换成你的
  s.setAttribute('data-category', 'General')
  s.setAttribute('data-category-id', '从 giscus.app 拿')  // ← 换成你的
  s.setAttribute('data-mapping', 'pathname')   // 按文章网址区分留言，一篇文章一个留言串
  s.setAttribute('data-theme', 'light')
  s.setAttribute('data-lang', 'zh-CN')
  box.value.appendChild(s)
}

onMounted(create)
</script>
```

那几个 ID 从哪拿？打开 **giscus.app/zh-CN**，填上你的仓库名，它会用「填空题」的方式一步步引导你，最后直接把一段配置发给你——里面就有 repo-id 和 category-id，照抄就行。

然后在网站设置（`docs/.vitepress/config.ts`）里注册这个组件，再在文章页面的模板里放一行 `<Giscus />`，留言板就挂上了。改文件保存，本地预览里就能看到。

### 我踩过的坑（这部分比代码值钱）

**坑一：留言板挂上了，读者却发不了言。**

Giscus 让你选一个讨论区分类。有个叫 Announcements（公告）的分类看起来很正经，我选了它，结果所有访客都只能看不能说——因为公告分类**只有管理员能发言**。换成 **General** 分类就好了。选之前想清楚：你要的是「读者能说话」，不是「我只发公告」。

**坑二：晚上开灯，留言板还是黑着。**

如果你的博客有深色模式，会发现留言板不跟着变。因为留言板其实是一个嵌进来的小网页，它不知道你的网站换了灯。解法是「隔空喊话」：检测到模式切换时，给留言板发一条消息让它换主题：

```js
iframe.contentWindow?.postMessage(
  { giscus: { setConfig: { theme: 'dark' } } },
  'https://giscus.app'
)
```

**坑三：从一篇文章点到另一篇，留言板不刷新。**

这种博客有个特点：文章之间切换不整页刷新，只在后台悄悄换内容（这样加载快）。但留言板不知道这事，还挂在第一篇文章上。解法是每次文章变化时把留言板拆下来重装一遍——听起来粗暴，实际上它加载很快，读者毫无察觉。

**坑四：给自己留个管理后门。**

我的博客有个小机关：站长解锁后，留言板标题旁边会多一个「管理评论」的链接，直达 GitHub 讨论区。要不要做随你，但至少把讨论区的网址收藏好——删广告、回留言都在那边操作。

### 第一讲收尾

加完评论，你的博客就从「印出来的书」变成了「有回音的地方」。写作最大的乐趣之一就是收到陌生人的留言——哪怕只有一条，也值得把它接回来。

## 给博客加阅读量

> 第二讲解决一个更小、但很多人偷偷在意的问题——**到底有没有人在看**。

### 为什么阅读量这事也有点麻烦

还是那个老问题：你的博客是提前印好的书，寄存在免费地皮上。一本书印出来之后，**没人知道它被翻开了多少次**——因为「数数」这件事需要一个活人站在门口，而你的博客连门都没有，只是一个网址。

想数数，就得找一个愿意帮你站门口的活人。好在真有这样的活人，而且免费：

**不蒜子**（busuanzi，谐音「不算子」）是一个免费的统计服务。你只需要在网页里说一句「帮我数着」，它就在你看不见的地方站岗，每个访客来了记一笔，然后把数字填回你的页面。

它的原理你可以想象成：每个打开你博客的浏览器，都会顺手帮不蒜子按一下计数器。计数器本身住在不蒜子的服务器上，你的页面只负责把数字显示出来。

### 三种数字，先想清楚要哪种

不蒜子一次能给你三个数：

- **这一篇文章被看了多少次**（页面阅读量）
- **全站被看了多少次**（站点总阅读量）
- **有多少个不同的人来过**（访客数，同一个人来十次只算一个）

我的选择：文章页只显示第一种的标题阅读量，首页页脚放后两个。数字一多就没人看了，而且访客数这种东西，越少越不忍看。

### 动手：两步搞定

**第一步**，在文章页面的代码里，把数字摆出来：

```html
<span id="busuanzi_value_page_pv"></span> 次阅读
```

不蒜子的规矩是：你放一个它认识的 `id`，它就把数字填进那个位置。三个数对应三个固定的 id：`busuanzi_value_page_pv`（本文）、`busuanzi_value_site_pv`（全站阅读）、`busuanzi_value_site_uv`（全站访客）。

**第二步**，在页面里请它开始工作：

```html
<script async src="https://busuanzi.ibruce.info/busuanzi/2.3/busuanzi.pure.mini.js"></script>
```

就这么简单。刷新页面，数字出现了。

### 我踩过的坑（照抄我少走弯路）

**坑一：数字填不上——它说「请先引入脚本」。**

如果你先放了数字的位置、后请的活人，可能碰上数字空着的情况。其实只要把脚本加上 `async`（让它不打扰页面加载）并稍微等半秒，数字都会跟上。我最后干脆封装了一个小函数：

```js
export function loadBusuanzi() {
  document.getElementById('busuanzi')?.remove()
  const s = document.createElement('script')
  s.id = 'busuanzi'
  s.src = 'https://busuanzi.ibruce.info/busuanzi/2.3/busuanzi.pure.mini.js'
  s.async = true
  document.body.appendChild(s)
}
```

**坑二：从这篇文章点到那篇，阅读量没变。**

跟评论区一模一样的问题——你的博客文章之间切换不整页刷新，不蒜子还以为你停在同一篇文章上。解法也一样粗暴有效：**每次切文章，把站岗的大爷重新请一遍**（把脚本标签删掉再插一个）。我的实现里还特意加了半秒延迟，让页面先画完，大爷再来报数，免得数字闪一下。

**坑三：它是个免费服务，也因此没有售后。**

不蒜子由一位开发者免费维护，历史上有过几次不稳定。它挂了，你的数字会暂时显示不出来（不会显示错，就是空着）。想清楚再上：如果阅读量对你只是「自我确认有人在看」，它的偶尔失联完全可以接受；如果你要做正经的数据分析，那得用别的方案（通常要注册统计服务、埋代码，也就不再是「两步搞定」了）。

### 第二讲收尾

加完阅读量，写文章的心情会有微妙的变化：知道有人在看，会更加认真；偶尔看到某个深夜的访客数 +1，也会莫名高兴一下。

但也要提醒一句——数字这个东西，看多了会反过来绑架写作。我的建议是像不蒜子的名字那样：数着，但不算计。

## 浏览器里一键发布是怎么做到的

> 第三讲掀开后台的帘子，讲我博客「创作」页那个按钮：写完文章点一下，**不用命令行、不用装任何软件，一分钟后文章就出现在网站上**。

### 回顾一下：正常发布要走哪几步

上面的「五步搭好博客」里，发布一篇文章要：

1. 在电脑上新建 `.md` 文件
2. `git add`、`git commit`、`git push`（打包装车 → 贴标签 → 发车）
3. 等 GitHub 自动重新印刷网站

问题出在第 2 步：它要求你在**自己的电脑上**、**装好 git**、**记得住咒语**。可写作的冲动经常发生在别人的电脑、公司的午休、只想改一个错别字的瞬间。

于是我想：能不能让**浏览器自己当邮差**，替我把书稿寄到 GitHub 的仓库去？

答案是能。GitHub 在自家仓库门口开了一个「快递窗口」，专门接收这种寄存请求。它叫 **GitHub API**。

### 第一件东西：一张门禁卡（Token）

快递窗口当然不能谁来了都收件——总得证明「这批货是我仓库的」。证明物就是 **Token（令牌）**：一串字符，相当于一张**门禁卡**。

这张卡有三个特点，恰好让它适合浏览器用：

- **只开一扇门**：GitHub 允许你造一张「只能操作某一个仓库」的卡。我给博客造的卡只打得开 Destiny 这一个仓库，别人家的门都试不了
- **只给一种权限**：还能进一步限制成「只能读写文件内容」，删库、改设置这些事它干不了
- **随时作废**：怀疑卡丢了？后台一点，卡就废了，再造一张新的

造卡的地方在 GitHub 的 **Settings → Personal access tokens**（个人访问令牌）。记住一个原则：**权限给得越少越安全**。一张只能往一个仓库放文件的卡，就算真泄露了，最坏结果也只是仓库里多个垃圾文件。

**关键安全细节**：这张卡只存在我电脑的浏览器里（浏览器有个自带的「贴身口袋」叫 localStorage，只属于这台设备这个浏览器），**绝不会写进仓库、不会出现在网站代码里**。所以读者就算翻遍整个网站，也找不到这张卡。

### 第二件东西：快递窗口的收件流程

有了卡，寄存一份文件就三步。假设要把一篇文章存到仓库的 `docs/posts/my-post.md`：

**第一步：先问一句「这个位置有东西吗」。**

```js
const get = await fetch(
  'https://api.github.com/repos/Destiny-wangchen/Destiny/contents/docs/posts/my-post.md',
  { headers: { Authorization: 'Bearer ' + token } }
)
```

- 返回「有」（状态 200）：说明是**修改老文章**，响应里会附带这件东西的「货号」（叫 **sha**，可以理解成仓库给每个版本发的编号）
- 返回「没有」（状态 404）：说明是**新文章**，直接寄
- 返回「没权限」之类（401/403）：多半是门禁卡过期了，程序会自动弹出填卡的框

**第二步：打包，寄出去。**

快递窗口有个奇怪的要求：**货物必须打成一种叫 base64 的包**。不用怕，这只是「把文字变成一长串字母数字」的打包方式，任何编程语言一行代码就能做：

```js
function b64encode(str) {
  const bytes = new TextEncoder().encode(str)
  let bin = ''
  bytes.forEach((b) => (bin += String.fromCharCode(b)))
  return btoa(bin)
}
```

然后连货带单一起寄：

```js
await fetch(url, {
  method: 'PUT',
  headers: { Authorization: 'Bearer ' + token, /* … */ },
  body: JSON.stringify({
    message: 'publish: 文章标题',   // 这次改动的一句话说明，和 git commit 的作用一样
    content: b64encode(markdown),   // 打包好的书稿
    branch: 'main',
    sha: sha                        // 修改老文件时必须带上货号（见下）
  })
})
```

**第三步：为什么改老文件要带「货号」（sha）？**

这是一个很聪明的防呆设计。想象两个人同时寄存同一件东西：甲寄了一份，乙不知道，也寄了一份——乙就会把甲的版本**悄悄覆盖掉**。有了货号制度，寄存修改版时必须报出「我拿到的是第几版」：如果仓库里已经是更新的版本，窗口会拒绝收件，你被迫先看一眼最新版，而不是造成无声的覆盖。

就像寄快递要核对取件码。核对不上，说明你手里的单子过期了。

**第三步之后：印刷机自己转起来。**

文件寄进仓库的那一刻，GitHub 检测到仓库更新了，自动触发[第 5 步配的自动部署](#第-5-步-打开「开放参观」的开关)：重新印刷、重新上架。一分钟左右，新文章出现在网站上。这也是为什么我的创作页发布成功后会给一个「查看构建进度」的链接——剩下的活儿是 GitHub 的，你只能等，但可以围观。

### 为什么要做这个功能（而不只是能做）

装好后最大的变化是：**发布这个动作消失了**。写完点一下，回到正文。

对一个博客来说这很重要——发布的门槛每高一点，就有一些本来会写出来的文章死在了草稿里。那些「懒得开电脑了」「下次再发吧」的念头，杀死的不只是文章。

### 我踩过的坑

**坑一：Token 权限不够，报错一脸懵。**

只给「读」权限时，每次 PUT 都失败。报错信息只有冷冰冰的 403。解法还是那张原则：卡的权限要包含「读写文件内容」（Contents: Read and write），别多也别少。

**坑二：修改老文章忘了带 sha。**

新建文章一路顺利，改老文章就报错。就是因为快递窗口要求修改时核对货号。我的做法永远是「先查再寄」：不管三七二十一先 GET 一次，有 sha 就带上，404 就当新建。

**坑三：Token 是不能公开的，别让它进仓库。**

再三强调：这张卡和你家钥匙一样。它只该出现在浏览器的贴身口袋里。如果你按这一讲自己实现，检查一遍代码——Token 相关的字样出现在任何会被上传的文件里，都是事故。

## 给博客加一个加密保险箱

> 最后一讲是我最得意的一个机关：怎么让一篇文章公开躺在免费的地皮上，却只有拿着密码的人能读。两个名词 PBKDF2 和 AES-GCM 听起来吓人，但拆开讲全是常识。别跳读，它们比想象中好懂。

### 需求本身就很拧巴

先摆一下难点，你会发现这个需求天然矛盾：

- 这个博客是按上面流程搭起来的免费静态站：所有文件提前印好，寄存在 GitHub 的免费地皮上，**没有服务器、没有数据库、没有任何「活人」在后台值守**
- 而加密这件事，直觉上应该有个「保险库管理员」：你把密码告诉管理员，管理员去库里帮你取东西

没有服务器，管理员在哪？密码交给谁？

### 换个思路：保险箱在读者家里现场组装

答案是把整件事反过来：**不让读者把密码送到保险库，而是把锁好的箱子寄到读者家里，让保险箱在读者自己的电脑上打开。**

具体流程是这样的：

1. 我在浏览器里写好一篇文章，填一个密码，点发布
2. 浏览器用这个密码把文章**当场锁进箱子**——锁的动作发生在我自己的电脑上
3. 寄到 GitHub 仓库去的是**一只上了锁的箱子**（一串谁也读不懂的密文），密码从头到尾没有离开我的电脑
4. 读者打开「密文」页，网页把箱子下载到**读者的浏览器里**，读者输入密码，箱子在**读者的电脑上**被打开
5. 密码同样没有离开读者的电脑

全程没有任何一台服务器见过密码，也没有任何一台服务器见过明文。GitHub 仓库里躺着的只是箱子。这就是「加密保险箱」的全部秘密：**没有管理员，因为每个读者家里都自带一个临时车间。**

浏览器天生就有这套开箱工具，名字叫 **crypto**（密码学工具箱），所有现代浏览器都内置，不用装任何东西。

### 工具箱里的两件宝

**第一件：PBKDF2，一台搅拌机。**

直接用密码当钥匙有个大漏洞：密码是人起的，往往不够乱。坏人拿到箱子，可以拿着一本「常见密码大全」挨个试——这叫暴力尝试。

PBKDF2 的解法像一台**搅拌机**：

- 把密码和一撮随机的**盐**（salt，一段随机字符，作用类似每道菜各放不同的调料）一起倒进去
- 搅拌 20 万次
- 倒出来的才是真正的钥匙

它的本质是「把一次尝试变得贵一点」：坏人每试一个密码，也得跟着搅拌 20 万次。你试一次要一秒，他试一万次就要几个小时。这道门槛不挡得住国家级的攻击，但绝对挡得住捡漏的人——对个人博客来说刚刚好。

盐还有一层作用：同样的密码「123456」，每次发布的盐都不一样，搅拌出来的钥匙也完全不同。坏人事先算好「123456 对应哪把钥匙」的对照表，在我这里就对不上了。

**第二件：AES-GCM，带封条的保险箱。**

AES 是全世界通用的锁具标准，你的手机加密、银行转账用的都是它家族的锁。GCM 是它的一个升级款，多了一个很妙的功能——**封条**。

普通保险箱被撬开过、箱子里的东西被掉过包，你可能都看不出来。GCM 不一样：**箱子哪怕被人改动了一个字，开箱时封条就会破裂**，浏览器直接报「解密失败」，绝不会把被篡改的内容当真递给你。密码错误和箱子被动过手脚，在这里是同一种结局：开不了。

### 上代码：其实就这么点

加密（发布时，在我电脑上跑）：

```js
async function encryptForVault(payload, password) {
  const salt = crypto.getRandomValues(new Uint8Array(16))  // 每篇文章现抓一撮盐
  const iv   = crypto.getRandomValues(new Uint8Array(12))  // 随机取一个「上锁姿势」
  const key = await crypto.subtle.deriveKey(
    { name: 'PBKDF2', salt, iterations: 200000, hash: 'SHA-256' },  // 搅拌 20 万次
    await crypto.subtle.importKey('raw', new TextEncoder().encode(password), 'PBKDF2', false, ['deriveKey']),
    { name: 'AES-GCM', length: 256 },
    false,
    ['encrypt']
  )
  const ct = await crypto.subtle.encrypt(
    { name: 'AES-GCM', iv }, key,
    new TextEncoder().encode(JSON.stringify(payload))       // 把标题、标签、正文一起装箱
  )
  return { salt: 到base64(salt), iv: 到base64(iv), ct: 到base64(ct), iter: 200000 }
}
```

解密（阅读时，在读者电脑上跑）是同一个流程倒着走：同样把密码和箱子上标注的盐倒进搅拌机，转同样的圈数（所以密文里要记录 `iter: 200000`，告诉读者家里的车间「这台机器要搅多少下」），配出同一把钥匙，然后开箱。密码不对，搅出来的钥匙对不上锁孔，GCM 封条破裂，报错。

### 箱子上挂的三个标签

寄到仓库的每个箱子是一个小小的 JSON 文件，长这样：

```json
{
  "id": "my-secret-note",
  "date": "2026-11-13",
  "salt": "（那撮盐）",
  "iv": "（上锁姿势）",
  "ct": "（密文）",
  "iter": 200000
}
```

三个标签都不是机密，可以光明正大贴在箱子上：

- **salt（盐）**：告诉读者家「搅拌时加这撮料」。盐不保密，保密的是密码
- **iv**：同一个密码、同一把钥匙，如果每次都「用完全相同的姿势上锁」，同开头的两篇文章会露出相同的密文花纹，容易被看出规律。所以每次上锁都换一个随机姿势
- **iter（圈数）**：告诉读者家「这台搅拌机要搅多少圈」。以后想升级到 60 万圈，老箱子还是标着 20 万圈，照样能开——各贴各的标签，互不影响

### 我踩过的坑

**坑一：忘了密码，谁都救不了。**

这是设计使然，不是缺陷：仓库里只有密文，我也没存密码——想存也存不了，因为连我自己都不知道怎么从密文里把密码变回来。所以给保险箱设密码时，要么用你绝对不会忘的，要么把密码记在可靠的地方。**忘记密码的文章，等于永远烧掉了。**

**坑二：别把「简单混淆」当成加密。**

我还做了个彩蛋功能：某个条目不设密码，用一个固定密钥「轻度混淆」，懂的读者能找到入口。它的定位是捉迷藏，不是保险箱——固定密钥就写在网页代码里，等于箱子旁边贴着钥匙的照片。混淆和加密是两个东西，别混用定位。

**坑三：加密只保护箱子里的内容，不保护「有一只箱子存在」这个事实。**

访客能看到密文页有一篇文章、发布于哪天、文件名是什么。真正的秘密（标题、标签、正文）都在箱子里。如果有连「存在本身」都要藏的内容，这个方案不覆盖——但说实话，个人博客大多数时候要藏的是内容，这就够了。

## 最后

这套东西搭好之后，你拥有的就是：一个**完全属于自己的、加载飞快的、永久免费的**小站。写作这件事，从此只和文字有关。

回头看，四讲加起来，每一步都是免费工具的组合，没有一步需要租服务器。这大概是我从这一路折腾里学到的最重要的事：**你想要的东西，往往已经有人免费造好了，缺的只是有人告诉你它们怎么拼在一起。**

希望这篇就是那声「有人告诉你」。
