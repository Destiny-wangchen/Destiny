## 主诉

有个同学在算"一条记录多大"，准备用 `fwrite` 整块写文件。他掰着手指算：一个 `char` 一字节，一个 `int` 四字节，再一个 `char` 一字节，一条 6 字节，一千条 6 KB，没问题。

结果文件写出来是 12 KB，正好翻倍。他把 `sizeof(struct)` 打出来，看到 12，人有点懵。

更懵的是，同宿舍另一个人把成员顺序换了一下，同样的成员，`sizeof` 变成 8。

## 化验

```c
#include <stdio.h>
#include <stddef.h>

struct S { char a; int b; char c; };     /* 1 + 4 + 1 */
struct T { int b; char a; char c; };     /* 同样的成员，换顺序 */
struct U { char c; double d; };

int main(void)
{
    printf("sizeof(S) = %d, offsetof(b) = %d\n",
           (int)sizeof(struct S), (int)offsetof(struct S, b));
    printf("sizeof(T) = %d\n", (int)sizeof(struct T));
    printf("sizeof(U) = %d, offsetof(d) = %d\n",
           (int)sizeof(struct U), (int)offsetof(struct U, d));
    return 0;
}
```

实测：

```text
sizeof(S) = 12, offsetof(b) = 4
sizeof(T) = 8
sizeof(U) = 16, offsetof(d) = 8
```

三个成员加起来 6 字节，`S` 占 12。`T` 成员一样，只换了顺序，占 8。

## 诊断：两条对齐规则

规则一，**每个成员的起始偏移必须是它自身大小的整数倍**。`S` 里 `a` 在 0，`b` 是 `int` 要 4 的倍数，0 后面最近的 4 的倍数是 4，所以 `a` 之后空 3 个字节，`b` 落在 4。`c` 落在 8。此时用了 9 字节。

规则二，**结构体总大小必须是最大对齐数的整数倍**，这样才能保证数组里每个元素的成员都对齐。`S` 最大对齐是 4，9 往上凑到 12，末尾又补 3 个字节。

`T` 先放 `int`（0～3），`a` 在 4，`c` 在 5，总共 6，凑到 4 的倍数变 8。省下来的 4 字节就是这么来的。

`U` 里有 `double`，对齐数是 8。`c` 在 0，`d` 必须落在 8，中间空 7 个字节，总共 16。

多出来的字节叫填充（padding），里面是什么值不确定，编译器不保证是 0。

## CPU 为什么要求对齐

这不是编译器的洁癖。64 位 CPU 访问内存是按"字"来的，一次搬 8 字节，地址必须是 8 的倍数。一个 `int` 如果横跨两个 8 字节块，CPU 要么读两次再拼起来，要么在某些架构上直接触发异常。

x86 比较宽容，不对齐也能跑，只是慢一点；ARM 上很多指令要求严格对齐，不对齐会直接崩。所以"我这能跑"不代表代码是对的。

这也解释了一个常见现象：同一个结构体，在 32 位和 64 位编译器下大小可能不同（`long` 和指针宽度变了），你按 `sizeof` 写文件、按固定长度读回来，换台机器就读歪了。

## 三个真实后果

**第一个，文件读写对不上。** 直接 `fwrite(&s, sizeof(s), 1, fp)` 把填充字节也写进去了。填充内容不确定，两个人写出的文件字节不同，做校验会失败；换编译器后 `sizeof` 变了，旧文件读不出来。

**第二个，`memcmp` 比较结构体。** 两个逻辑上相等的结构体，填充字节不同，`memcmp` 判不等。这个坑在网络包对比、缓存命中判断里很常见。

**第三个，网络传输。** 结构体直接扔进 socket，对端如果对齐规则不同，字段全部错位。协议里的字段顺序和宽度是定死的，不能靠 `sizeof` 猜。

## 处方

1. 按大小从大到小排成员。`double`、指针、`int`、`short`、`char` 这个顺序，填充最少。这是零成本的优化。
2. 跨进程、跨文件、跨网络不要直接写结构体。逐字段序列化，或者用固定宽度的 `uint32_t` 之类，把字节序也定下来。
3. `#pragma pack(1)` 能取消填充，但会让成员不对齐，访问变慢，甚至在某些平台崩。只在解析外部协议时用，用完立刻 `#pragma pack()` 恢复。
4. 用 `offsetof` 而不是手算偏移。`sizeof` 和 `offsetof` 都写进断言里，换平台能第一时间发现。
5. 别用 `memcmp` 比较含填充的结构体，逐字段比。

## 复诊

对齐本身不难，难的是它会在你完全想不到的地方冒出来：文件大小对不上、网络包解析错位、`malloc` 出来的内存算错偏移。练手的话，[第 6 章 · 数组](/cbook/06-shuzu.html) 里二维数组的地址计算是同一套逻辑（行优先 + 步长），值得重看一遍。
