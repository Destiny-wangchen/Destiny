## 主诉

先讲个我自己的场面。程序是同学发来的，统共十来行，逻辑一眼看到底。我在 Dev-C++ 里按 F11，黑窗口弹出来，还没等我看清有没有输出，窗口就没了。没有报错，没有提示，任务管理器里也找不到痕迹。我以为是 Dev-C++ 抽风，关掉重开，还是一样。

第二遍我把代码从头读到尾，唯一可疑的是这一行：

```c
int main(void)
{
    int loc[1000000];   /* 一百万个 int */
    /* ... */
}
```

试着删掉它，程序能跑；加一句 `getchar()` 想在崩之前停住，也没用，窗口照样一闪就关。最后是很偶然地把这一行挪到 `main` 外面，程序第一次正常输出了结果。

同一份代码，同样的逻辑，只是换了个位置。这件事我记了很久，因为它是那种"知道答案之后觉得简单，不知道的时候完全无从下手"的问题。

## 先自己跑一遍

在 Dev-C++ 里新建一个 Console Application，把下面这段粘进去：

```c
#include <stdio.h>

int main(void)
{
    int loc[1000000];       /* 1000000 × 4 字节 ≈ 4 MB */
    loc[0] = 1;
    loc[999999] = 2;
    printf("%d %d\n", loc[0], loc[999999]);
    return 0;
}
```

按 F11，你会看到窗口一闪而过。想看它到底怎么死的，打开 cmd，`cd` 到 exe 所在的目录，运行：

```text
stack.exe
echo %errorlevel%
```

得到的不是 0，而是一个很难看的负数：`-1073741571`。换成十六进制是 `0xC00000FD`，这个编号在 Windows 里叫 `STATUS_STACK_OVERFLOW`，翻译过来就是栈溢出。

这里有两个容易误会的点，先说清楚。

第一，程序不是"算到一半出错"，是**进程刚起来就被系统杀掉了**。栈空间是在函数入口一次性划出来的，还没执行到任何一句 `printf`，容量就已经不够了。所以你加多少 `printf`、加多少 `getchar()`，一句也不会打印。

第二，退出码为什么是负数。Windows 的错误码用 32 位无符号数表示，命令行里 `%errorlevel%` 却是有符号的，最高位为 1 的数就被显示成了负数。`0xC00000FD` 和 `-1073741571` 是同一个东西，别被吓到。

## 查体：五个区

一个跑起来的 C 程序，内存大致分成五块。

<img src="./figs/case01-memory.svg" alt="C 程序的内存分区示意：代码段、数据段、BSS、堆与栈">

| 区 | 放什么 | 谁来分配 | 什么时候回收 |
|---|---|---|---|
| 代码段 text | 编译出来的机器指令 | 编译器生成，加载器映射 | 进程结束 |
| 数据段 data | 初始化过的全局变量、`static` | 编译器 | 进程结束 |
| BSS | 没初始化（或初始化为 0）的全局变量、`static` | 加载时由系统整块清零 | 进程结束 |
| 堆 heap | `malloc` 出来的内存 | 你 | `free`，或者进程结束 |
| 栈 stack | 局部变量、函数参数、返回地址 | 函数调用时自动分配 | 函数返回时自动回收 |

顺着这张表，可以把第 01 例的现场还原出来：`loc` 是局部变量，进 `main` 的时候老老实实被划在栈上，4 MB 一次要齐，栈拿不出来，进程当场结束。

教材上那张图，通常把堆画在栈下面，两个箭头对着长。这张图也一样，但我得提前说一句：**真实地址并不按这张图排**。下面化验的时候你会看到。

## 化验：三个地址

把刚才的数组挪到全局，再加一行 `malloc`，打印三个地址：

```c
#include <stdio.h>
#include <stdlib.h>

int g[1000000];          /* 全局，落在 BSS */

int main(void)
{
    int local_small = 0;
    int *p = (int *)malloc(sizeof(int) * 1000000);

    printf("g            = %p\n", (void *)g);
    printf("p (heap)     = %p\n", (void *)p);
    printf("&local_small = %p\n", (void *)&local_small);

    free(p);
    return 0;
}
```

我这台机器上（Windows + Dev-C++ 自带的 MinGW）跑出来是这样：

```text
g            = 0000000000407A40
p (heap)     = 0000000000F6D040
&local_small = 00000000009FFE44
```

三点观察。

三个地址差得极远，说明它们确实不住在同一个区。全局数组待在很低的地址，堆在中间偏上，栈在更高处。你换一台机器、换一个编译器，数字会全变，但"它们互相离得很远"这一点不会变。

堆的地址比栈还高。这跟教材那张图正好相反，因为那张图是逻辑分区的示意，不是 Windows 的真实布局。所以下次看到别人的运行结果和书上对不上，先别急着怀疑自己抄错了。

栈确实是往下长的。写个小实验就能看见：

```c
#include <stdio.h>

void inner(int depth)
{
    int here = 0;
    printf("第 %d 层 = %p\n", depth, (void *)&here);
    if (depth < 3) inner(depth + 1);
}

int main(void)
{
    inner(1);
    return 0;
}
```

输出三行，地址一层比一层小：

```text
第 1 层 = 000000000062FE1C
第 2 层 = 000000000062FDDC
第 3 层 = 000000000062FD9C
```

每调用一层，栈指针往下退 64 字节（这里正好是 0x40），函数返回再退回去。这就解释了为什么递归太深会崩：每层都要在栈上占一块，占的时候往下走，走到底就是刚才那个 `0xC00000FD`。

顺手说一句 `%p` 前面为什么要写 `(void *)`。`printf` 的 `%p` 只认 `void *`，别的指针类型硬传进去在标准里属于未定义行为。MinGW 通常只是给个警告，换个编译器可能就打出一个奇怪的地址，让你误以为变量位置不对。

## 诊断：不是数组太大，是放错了区

一百万个 `int` 是 4 000 000 字节，约 3.81 MiB。而 Windows 给每个线程的栈默认只有 1 MiB，Linux 是 8 MiB。还没开始算，就已经越界了。

所以问题从来不是"数组太大"。同样 4 MB 的数组放在全局一点事没有，我上面那个例子就把 4 MB 放在 BSS 里，跑得很稳。真正的问题是**它被放在了最小的那个区里**。

栈为什么这么小？因为它是每个线程一份的。一个进程开 8 个线程，栈就是 8 份。系统宁可把默认值设小，让你在需要的时候自己调，也不愿意每个线程一上来就预占 8 MB，八个线程就是 64 MB，白白浪费给不写递归的程序。

想验证这个说法，把栈调大再跑一次：

```text
gcc -std=c11 -o stackbig.exe stack.c -Wl,--stack,8388608
```

同样一段代码，同样 4 MB 的局部数组，这回正常输出了。在 Dev-C++ 里对应"项目属性 → 参数 → 链接器"，填 `-Wl,--stack,8388608`，重新编译即可。

但这是止血，不是治病。栈调大之后，递归写错照样崩，只是崩得晚一点，而且这种崩更难查，因为它在别人的机器上可能不发生。真正该做的是别把大块数据塞进栈。

顺带记三种"塞进栈"的方式，症状和第 01 例一模一样，换个说法你可能也遇到过：

- 函数里定义大数组，也就是本例；
- 递归层数太深，每层几十到几百字节，累计起来就爆了；
- 变长数组 `int a[n]` 和 `alloca`，大小运行期才知道，编译器没法提前拦你。

## 顺手解释另一个症状

既然讲到了 BSS，有个问题可以顺手说清：为什么全局数组不初始化就是 0，局部变量不初始化却是垃圾值？

因为 BSS 段在程序加载时被系统整块清零，这是操作系统干的活，和你的代码无关。而栈上的内存是反复压入、弹出的旧地方，上一个函数留下的数据还在那儿，没人给你擦。你写 `int x;` 只是把栈指针挪了一下，并没有写入任何东西，读出来自然就是别人剩下的。

网上常说的"烫烫烫"是另一回事。MSVC 在调试模式下会把未初始化的栈填成 `0xCC`，连续两个字节 `CC CC` 在 GBK 里正好是"烫"字。这是编译器的调试填充，不是标准，MinGW 下就不保证有。所以看到"烫烫烫"能断言"你用了没初始化的内存"，但看不到不代表没问题。

## 常见误诊

这类崩溃之所以难查，是因为症状太含糊：一个没有任何输出的进程，可以被解释成十种病。下面四个方向我都走错过，记下来省点时间。

**误诊一，内存泄漏。** 泄漏的前提是程序跑起来了、一直在申请内存。这里连第一句都没执行，而且泄漏影响的是堆，地址根本不在崩掉的那个区。

**误诊二，编译器或 IDE 坏了。** 把同一份代码丢给命令行的 `gcc` 编译，照样崩。IDE 只是帮你按了运行键，它不背这个锅。

**误诊三，内存条不够。** 4 MB 对 16 GB 的机器不算什么，卡住的是栈的容量上限，不是物理内存。这也是"别人的电脑能跑、我的不行"的常见来源，两台机器的栈默认值可能就不一样。

**误诊四，杀毒软件在拦。** 加白名单、关掉实时防护再跑，依然崩。杀软拦截通常有弹窗或日志，栈溢出什么都没有。

判断顺序可以简化成这张表：

| 现象 | 先查什么 | 大概率的结论 |
|---|---|---|
| 双击就退，没有任何输出 | 退出码 | `0xC00000FD` 是栈溢出；其他负数先查 Windows 错误码 |
| 输出到一半停住 | 最后一次 `printf` 之后那句 | 越界写、空指针、`scanf` 读错类型 |
| 只在数据量大时崩 | 局部数组大小、递归深度 | 栈不够，数据放错区 |
| 换台电脑就好了 | 栈默认值、类型宽度、字节序 | 可移植性问题，不是逻辑错 |

## 处方

1. 大数组放全局或 `static`。这是最省事的一条，代价是它会在整个程序生命周期里占着内存。
2. 大小要运行时才知道，就用 `malloc`，并且检查返回值是不是 `NULL`。
3. 记两个经验阈值：`int` 超过 25 万个（约 1 MiB）就该警惕栈，`char` 是 100 万个。再大就想想是不是该放到堆上。
4. 写递归之前估一下深度。每层假设占 100 字节，一万层就是 1 MB，正好把默认栈用光。
5. 只在确实需要时调栈大小，别把它当成默认操作。
