## 主诉

新学 C 的人最常问的两个问题，其实是同一个问题的两面：

"我明明写了 `#include <math.h>`，为什么还报 `undefined reference to sqrt`？"

"我改了头文件，为什么程序还是老样子？"

第一个看着像语法错误，第二个看着像缓存问题。它们都发生在编译和链接这两个不同的阶段，搞清楚这四步，两类问题自己就能定位。

## 化验：一个 hello 的四个形态

准备一个 114 字节的源文件：

```c
#include <stdio.h>
#define NAME "clinic"

int main(void)
{
    printf("hello, %s\n", NAME);
    return 0;
}
```

用 `gcc` 分四步走，每一步留下一个产物：

```text
gcc -E hello.c -o hello.i    预处理：展开头文件和宏
gcc -S hello.c -o hello.s    编译：C 变成汇编
gcc -c hello.c -o hello.o    汇编：汇编变成机器码 + 符号表
gcc    hello.c -o hello.exe  链接：拼成可执行文件
```

我这台机器上的产物：

| 文件 | 大小 | 行数 | 内容 |
|---|---|---|---|
| `hello.c` | 114 B | 8 | 你写的东西 |
| `hello.i` | 34 094 B | 485 | 头文件全展开后的 C 代码 |
| `hello.s` | 572 B | 30 | x86-64 汇编 |
| `hello.o` | 892 B | — | 机器码 + 符号表 |
| `hello.exe` | 131 002 B | — | 加了启动代码和 C 运行库 |

一个 114 字节的文件，最后变成 131 KB 的程序。多出来的部分不是你的代码，是运行时必须要有的启动代码、库函数、调试信息。

## 诊断：四个阶段，各管一段

**预处理。** 处理所有以 `#` 开头的行：把 `stdio.h` 的内容原样拷进来（这就是 34 KB 的来源），把 `NAME` 替换成 `"clinic"`，按 `#ifdef` 决定哪段代码留下。这一步不做语法检查，所以宏写错了往往要到下一步才报。

**编译。** 把 C 代码翻译成汇编。语法错误、类型不匹配、未声明变量全在这一步报，错误信息里有 `文件:行号`。这一步是"翻译"，不管函数到底存不存在。

**汇编。** 把汇编翻译成机器码，生成 `.o` 文件。`.o` 里除了机器码，还有一张**符号表**：这个文件定义了哪些函数（`T` 开头），引用了哪些还没找到的外部符号（`U` 开头）。

**链接。** 把所有 `.o` 和库拼起来，给每个 `U` 符号找到对应的 `T`。找不到就是 `undefined reference`，找到两个就是 `multiple definition`。

## 三个典型错误，各在哪一层

**编译期错误**：`expected ';'`、`implicit declaration of function`、`incompatible types`。看 `文件:行号`，改代码。

**链接期错误**：`undefined reference to 'sqrt'`。你的代码没问题，是库里没接上。数学库在 Linux 上要显式加 `-lm`，命令行写 `gcc main.c -lm -o main`，库参数要放在源文件后面。Windows 的 MinGW 通常自动带上，所以很多人换到 Linux 才发现。

**链接期错误之二**：`multiple definition of 'foo'`。最常见的原因是把函数**定义**写进了头文件，然后被两个 `.c` 同时 include。头文件里只放声明，定义放 `.c`。

还有一类容易混淆：`main` 拼成 `mian`，编译完全通过，链接时报 `undefined reference to 'main'`。编译器不知道你少打了字，它只知道没人提供入口。

## 一个实用技巧：改不动的时候看 `.i`

"我改了头文件为什么没生效"这个问题的答案，九成在预处理产物里。

把 `hello.i` 打开，搜你改的那个宏名或结构体名，看它到底展开成了什么。有时候是你改的文件没被 include 进来，有时候是另一个同名宏在后面把它覆盖了，有时候是条件编译把它整段砍掉了。这些在 `.c` 里都看不出来，在 `.i` 里一目了然。

想看符号表就用 `nm hello.o`：

```text
0000000000000000 T main
                 U printf
```

`T` 是我提供的，`U` 是别人要提供的。链接器干的就是把 `U` 变成 `T` 的活。

## 处方

1. 报错先分阶段。看到 `file:line: error` 是编译期，看到 `undefined reference`、`multiple definition` 是链接期，运行起来才崩是运行期。三类错误的查法完全不同，别混着找。
2. 头文件只放声明。函数体、变量定义放 `.c`，否则迟早撞 `multiple definition`。
3. 编译选项打开 `-Wall -Wextra`。`implicit declaration` 这种警告在 C99 之后其实是错误的信号，被忽略一次，后面就要靠猜参数类型。
4. 大型项目用 Makefile 或 CMake，别手敲一长串 `gcc`。手敲最容易漏 `-lm`、漏某个 `.c`。
5. 排查诡异问题就分步走：`-E` 看宏，`-S` 看汇编，`nm` 看符号。三步下来基本没有定位不到的问题。

## 复诊

四步里最容易出错的是链接，因为它牵扯到"谁提供、谁使用"的关系，而 C 语言靠头文件手工维持这种约定。等你写多文件程序时，[第 8 章 · 函数与递归](/cbook/08-hanshu.html) 里那种"函数声明和定义分家"的写法就是最小规模的演练。
